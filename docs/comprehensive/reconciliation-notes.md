# Reconciliation notes for Claude

1. Product catalogue, product codes, prices, paid-order entitlement and lifecycle remain outside this lane. The Comprehensive presentation layer accepts product metadata and reviewer input through props/contracts.
2. The future integration seam is `fromAssembledReportData(data, reviewerInput)` in `src/lib/reports/comprehensive/contract.ts`. The API/order lane should supply the assembled deterministic report data and persisted reviewer fields into this adapter.
3. Evidence-review persistence should map to `ReviewerEvidenceReview`, `ReviewerFindingReview`, `ReviewerRiskReview`, `ReviewerControlDesignReview`, `ReviewerDecisionReview`, `ReviewerObservation` and `ManagementDecision`. Do not map reviewer text into assessment answers or score-run fields.
4. The workbook builder is intentionally a new layer. The certified Essential supporting-register builder is not modified.
5. PDF generation is intentionally a separate future wiring step. The lane supplies HTML renderers; paid-order/API code should decide when to render and store them.
6. Product metadata for `TierComparison` is supplied via props. Do not hard-code the authoritative product code, price or entitlement inside the component.
7. Legal/privacy policy remains the source of truth for retention periods. The evidence request pack only asks for minimum necessary business records and includes a privacy boundary note.
8. Backend evidence statuses are mapped explicitly by `adaptBackendEvidenceStatus()` in `src/lib/reports/comprehensive/types.ts`: `not_requested → NOT_REQUESTED`, `requested → REQUESTED`, `received → RECEIVED`, `reviewed → EVIDENCE_REVIEWED`, `supported → VALIDATED_SUPPORTED`, `not_supported → NOT_SUPPORTED`, `insufficient → NOT_VALIDATED_INSUFFICIENT`, and `not_applicable → NOT_APPLICABLE`. `REVIEWER_JUDGEMENT` remains a separate human interpretation dimension and is never used as an evidence-item status.
9. Finding-level support requires an explicit `ReviewerFindingReview` with a non-empty `evidenceRefs` list, references that resolve to linked evidence actually reviewed, and `reviewerConclusion: 'SUPPORTED'`. A supported evidence item alone never promotes the whole finding. Negative or insufficient evidence requires an explicit coherent reviewer explanation before a supported finding conclusion can be recorded.
10. The Comprehensive main report uses `buildComprehensiveProjection()` as a bounded L2 view. It selects a maximum of 20 findings, 12 risks, 8 scenarios, 20 control actions and 24 dependency-closed roadmap actions; the complete L1 universe remains in the annotated register.
